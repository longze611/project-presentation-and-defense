# 流程与分点：参考PPT的信息呈现语法

本文件控制第一阶段图片中的信息组织。先根据内容关系选结构，再采用对应参考的视觉外观。每页从 [参考路由](../assets/reference-routing.json) 选择实际图片传入生成工具。以下比例来自页面观察的近似，不是原始对象的精确测量。

## 1. 先标注关系，不先决定画几个框

将当前材料拆成：核心主题、分组标签、每组解释、证据、结论，以及必要的顺序/依赖/反馈关系。

- 并列：同层级研究内容、指标维度、挑战、研究方法类别。用等层级分区，数量按内容决定。
- 顺序：前一步产出成为下一步输入。用有方向的流程及明确输入输出。
- 层级：大系统含子系统、层包含功能。用嵌套边界或分层，不用一串箭头冒充包含关系。
- 对应：一个问题对应一个方法，一个维度对应一种观察。用行、列或编号建立映射。
- 比较：同一口径下的方法或结果。用对齐列、表格、对照图，不暗示因果。
- 反馈：真实存在回流或迭代才画返回箭头。参考B第11页的跑道形六步布局可以只是排布，不代表算法无条件循环。

## 2. 蓝标签＋浅色解释条：分点的首选形式

源依据：A第7、16页，B第12页。参考图：[A分类解释](../assets/references/a-research.png)、[A标签与证据](../assets/references/a-label-rows.png)、[B维度解释](../assets/references/b-point-rows.png)。

每一行由一个短标签和解释组成。蓝色标签白字，浅灰蓝解释区放黑色正文，必要时加粗术语和红色关键词。行高、标签宽、正文起点一致，行之间有明确间隔。标签一般2—8字或短英文缩写，解释用1—3行。

有共同研究对象时，在左侧约20%—25%放真实对象图或短概念图，右侧约70%—75%排2—5行解释；没有对象图时横条可占主体全宽。每行可细分为“维度标签—核心定义—判定方法”，而不是只有一个抽象词。

生成指令：

```text
按所附B第12页组织分点：左侧保留共同对象，右侧将{N}个并列维度排成等宽横向行。每行从左到右为深蓝白字短标签、浅蓝底黑色加粗定义、1—2条解释。行顺序和对应关系按输入，不补成固定三条。统一标签宽度与文字基线，底部仅在有明确总结时放一条短结论。
```

## 3. 分类侧签＋解释内容：多层分点

源依据：A第7页、A第18页、B第15—16页。用竖向蓝侧签统领一组解释，侧签右边为一个或多个浅色内容块。适合“样本处理/数据分析/系统优化”这类层级分类，或“输入/证据/判定”三类不同信息。

侧签宽度约主体区的8%—15%，根据标签长度调整。分类不超过4字时可以竖排，长术语用横排避免逐字断裂。每组内部只用必要细分线，不让各组共享一个无法判断边界的大段落。

生成指令：

```text
将{分类列表}逐组纵向排列，每组左侧蓝色侧签标识类别，右侧浅色区放对应解释和证据。组间留白大于组内段距。不要把{分类}误画成先后步骤，不加过程箭头。
```

## 4. 等层并列研究模块

源依据：A第4、8页，B第4页。[A并列任务](../assets/references/a-parallel.png)、[B双挑战](../assets/references/b-challenges.png)。

采用2—3列为常见起点，各列蓝色标题/浅蓝标题区，下方白或极浅底正文、真实证据图和局部结论。列标题同级，主体内容从相同基线开始。共同结论可跨整页放在下方。每列中按“主题—说明—证据—判断”组织，不做只有图标和一句口号的空白卡片。

若内容是对等任务，不因原图有箭头就强加依赖。若内容是两个问题，各列应明确自己的证据和缺口，不把一列结论挪到另一列。

## 5. 左问题分点＋右局部系统图

源依据：B第9、13页。[问题页](../assets/references/b-painpoints.png)。左侧约50%—55%为浅边框内容区，按“问题1/问题2”等蓝色小标题分段，下面黑色解释，粗体突出关键限制；右侧约40%—45%放与问题相关的真实系统子图。

图与问题直接对应，不能用领域相关却不解释问题的插画填空。非当前大模块在标题中可弱化，当前模块保持蓝色强度。不能把重要正文也变成极浅灰。

## 6. 系统总图＋局部定位＋分图解释

源依据：B第7—10、13—16页。[系统图](../assets/references/b-system.png)、[方法定位](../assets/references/b-method-overview.png)。

先给完整系统，建立输入、模块、输出及模块边界。后续页复用相同总图或忠实对应的子图，用红色细框突出当前区域，再展开机制页。这里重复总图属于导航功能，不能因为追求每页不同而不断重绘另一套架构。

红框围住实际相关节点，红色引线指向对应解释，不横跨无关节点或遮挡原有连线。多个标注一一对应，不能仅凭颜色让读者猜哪条解释对应哪里。需要放大细节时，明确局部与全图的关系。

## 7. 主方法图＋侧栏分点

源依据：B第10、11、14页，A第11页。[机制与解释](../assets/references/b-method.png)。主体左侧约60%—70%是方法图，右侧约30%—40%为2—4条机制/效果解释。右侧短条或分区沿纵向排列，蓝标题或蓝色加粗句建立阅读顺序。

图内可以用短编号显示步骤；图外分点解释“做了什么、为什么、带来什么影响”。图内外术语一致，不用不同名字描述同一模块。真实结果与待验证收益必须区分。

参考B第11页使用蓝色跑道式六步布局。只有节点数量和关系适合时才选此结构；不要把所有算法都画成跑道，不为了外形增加不存在的两步。

## 8. 左纵向步骤＋右侧科研证据

源依据：A第12页。[纵向流程](../assets/references/a-vertical-flow.png)。左侧约18%—23%放顺序步骤，白底蓝字的步骤块之间用蓝色向下箭头连接；右侧约75%为对应实验图、装置图或结果证据，下方短结论。

适合采集、预处理、建模、评价等顺序链。步骤间的箭头要有逻辑；证据右区能看到哪个图支撑哪个步骤。不要让流程列只有大字，而证据图小到不可读。

## 9. 分层架构与嵌套模块

源依据：B第22页。[分层架构](../assets/references/b-layered-architecture.png)。左侧窄层级标签，右侧按业务/功能/数据等真实层次横向分区。每层内部再按模块分组，模块内用对齐短文本或功能单元表达组成。

整体层使用浅灰背景，子模块用浅蓝等低饱和底，最小功能单元保持白底细边。嵌套是包含关系，不自动画全连接箭头。模块多时优先保证标签可读和层级清晰，可拆成“总体架构＋局部放大”。

## 10. 结构化证据链与公式

源依据：B第15、16、19页。[证据链](../assets/references/b-evidence-chain.png)、[验证对照](../assets/references/b-validation.png)。

上部1—2条文字交代方法；左侧放原始输入、结构化表或字段示例，右侧按检索、证据、公式、判定等步骤分区。蓝色标签告诉读者每块证据的角色；公式旁给符号含义和判断条件。

代码只保留解释机制所需的短片段，不能用不可读密集代码营造技术感。验证页要同时呈现正确、错误和证据不足等真实情况，不把局部成功扩大为全面有效。

## 11. 图表＋数值表＋短解释

源依据：B第18页。[实验页](../assets/references/b-experiment.png)。左侧约40%—45%为对齐数值表，右侧以比较图和趋势图解释不同层面的结果，关键方法/数值红色突出。正文说明与紧邻证据对应。

图表颜色可以包含灰、粉、绿等真实数据系列；蓝白是页面结构色，不代表所有科研图必须改成蓝色。不得复制参考数据、奖杯或夸张增幅到新课题。

## 12. 这些版式如何写入逐页计划

每页补充：`relation_type`、`presentation_pattern`、`reference_ids`、`groups`、`nodes`、`edges`。没有流程就不写虚构边；没有实验证据就不占位为真实结果图。

```json
{
  "relation_type": "parallel-dimensions",
  "presentation_pattern": "blue-label-rows",
  "reference_ids": ["B12"],
  "groups": [
    {"label": "准确短标签", "definition": "核心定义", "details": ["真实解释"], "evidence_ref": null}
  ],
  "nodes": [],
  "edges": []
}
```

最后检查：分组能否一眼辨认、标签与解释是否对齐、流程方向是否明确、颜色是否承担稳定语义、证据与结论是否相邻、整页是否仍像参考中的学术技术汇报。不能仅凭用了蓝色和矩形就判定匹配。

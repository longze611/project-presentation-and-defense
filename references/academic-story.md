# 学术内容组织：按用途选择叙事

## 先匹配用途，再组织页序

视觉风格统一，内容骨架随用途变化，不默认把所有学术材料转为开题答辩。

| 用途 | 主要叙事 | 不默认加入 |
|---|---|---|
| 论文精读/文献分享 | 研究问题、已有局限、核心方法、公式机制、实验、局限与讨论 | 自己的导师和研究进度 |
| 文献综述 | 问题分类、方法谱系、对照维度、证据比较、开放问题 | 每篇论文都单独做一套开题结构 |
| 组会进展 | 本阶段目标、已做工作、实验与分析、当前问题、下一步 | 正式致谢页、无关研究背景 |
| 方法/课程讲解 | 概念、机制、流程、例子、边界与比较 | 人员团队和项目风险 |
| 学术会议报告 | 研究问题、方法贡献、核心证据、结论与局限 | 冗长目录和任务分工 |
| 科研项目汇报 | 封面、目录；需求、研究任务、技术路线、证据、完成度与后续安排；结尾 | 与项目无关的竞赛身份 |
| 开题/中期/终期答辩 | 按真实阶段安排问题、计划、进展或结果 | 未发生的实验和成果 |

各用途都沿用参考的“明确主题—有标签分组—方法/证据—关键判断”信息组织。项目报告必须有封面、目录、结尾；其他用途按实际需要安排这三类页面。

## 页数、语言与文案确认

写文案前确认总页数和语言（中文或英文）；已明确的项不再问，未明确语言时不能根据论文原文或聊天语言自行推断。用户指定其他语言或双语时采用其要求。按 [启动流程](preflight-and-credentials.md) 完成生图测试，或取得明确跳过决定后，再开始逐页文案。总数包含封面、目录、正文、结尾及任何过渡/文献/备用页，除非用户明确允许某类页另计。用户说“约N页”时先以N页编写并在文案中标明实际总数，确认后以该数为准。

每页向用户呈现：页码与角色、标题、全部实际上屏文案、必要的表头/行标签/图注，以及流程节点和关键连接关系；图像位置、布局建议和讲稿另列，不能混为上屏文字。全部上屏文本（含封面、目录、结尾、标签与图注）使用已确认语言，论文题名、作者、引用、缩写、代码和公式保留必要原文；英文稿不能残留无意的中文模板。尚缺事实标注“待补”，说明是省略还是需要用户补齐，不把占位内容作为已确认事实。询问用户是否需要修改，并等其明确确认再启动正式页面生图或PPT制作；启动诊断图是唯一例外。修改后展示修订稿并等待确认，不以一句“已收到修改”直接开始制作。

项目报告的文案结构和设计须一同规划：

- 第1页 `cover`：真实项目题目、汇报类型，按已知信息写汇报人、单位和日期。未知信息不编造；无必要则省略。导师、竞赛标识和团队编号不默认继承。
- 第2页 `agenda`：列出实际正文的章节名称和顺序，通常3—5组；短报告可更少。目录条目必须与正文分组对应，不机械复制参考的五项或四项原文，不列没有正文支撑的章节。
- 中间 `body`：按本次汇报目的分配需求、目标/任务、方案与流程、证据/进展、下一步等。用剩余N−3页组织内容，不为套模板虚构研究任务。章节过渡页可选，重复目录不是必需，使用时仍计入总数。
- 最后1页 `closing`：写出符合受众的实际结束语，如“感谢各位专家，敬请批评指正！”或“汇报完毕，敬请指导！”，可补真实汇报人或项目简称。首尾使用同一家族设计。若需总结结论，在正文末页安排，不以密集总结页替代结尾。

若指定页数无法同时容纳三类必要页与有意义的正文，向用户说明并请求调整页数或明确例外，不能默默删掉目录/结尾或超出页数。确认过的文案修改事实、论点、页序后需重新审定；只修字距、换行、重叠与连线无需重复审批。

## 内容真源

以用户的论文/开题报告、数据文件、已发表材料、导师意见为依据。把研究现状、研究假设、计划工作、已有成果分开记录。每个定量值保留数值、单位、统计范围、比较基线和出处；每个公式保留LaTeX或数学源文本及变量定义。

文献表至少记录作者、年份、题名、发表源和可验证链接/DOI。找不到的条目不补造。文献原文或用户材料未支持的“首创”“显著领先”“国际先进”等表述不写。若引用间存在口径差异，说明条件，不合并为一个看似精确的数值。

开题重点是“为什么值得做、具体研究什么、怎样验证、是否做得成”。不能把参考B的产品介绍或竞赛成果直接套成开题结构。中期稿强调已完成和未完成；终期答辩可用真实结果替代计划页。

## 开题场景示例：15分钟、18页

仅在用户需要开题报告时参考下表，不是技能默认骨架。用户指定的总页数优先，18页包含封面、目录和结束页。

| 页 | 内容 | 推荐页型 |
|---|---|---|
| 01 | 研究题目、汇报人、导师、学院、日期 | A-cover或B-cover |
| 02 | 研究背景、问题目标、内容方法、验证安排 | Agenda |
| 03 | 研究背景与实际需求 | Background |
| 04 | 国内外研究现状与路线分类 | Related-work |
| 05 | 关键研究缺口与适用边界 | Background |
| 06 | 科学问题或核心技术问题 | Question |
| 07 | 研究目标与验证标准 | Question |
| 08 | 总体研究框架 | Overview |
| 09 | 研究内容一及其机制 | Method |
| 10 | 研究内容二及其机制 | Method |
| 11 | 技术路线与关键关系/公式 | Overview或Formula |
| 12 | 拟创新点及与已有方法的差异 | Related-work或Method |
| 13 | 实验设计、数据集与评价指标 | Experiment-plan |
| 14 | 可行性与已有研究基础 | Evidence |
| 15 | 时间计划与里程碑 | Timeline |
| 16 | 预期成果与主要风险 | Risk |
| 17 | 主要参考文献 | References |
| 18 | 结束页 | Closing |

不为了凑结构虚构第三个研究内容。若有三个真正不同的任务，可合并相邻正文内容或调整文献呈现以保持指定总页数；项目报告不得因此删去独立目录。备用页也计入总数，除非用户明确允许另计。

时长分配建议：背景和现状约20%，问题目标约15%，研究方案与技术路线约40%，实验和可行性约15%，计划成果风险约10%。18页不等于每页固定50秒，核心方法应留更多讲述时间。

## 每页信息密度

- 一页服务一个明确论点，正文优先3—5条，每条约15—30个汉字。专业定义必要时可更长，先简化句子再决定是否拆页。
- 英文稿按相同信息层级重新组织自然句子，以每条约8—18个英文词、正文页约50—100词为起点，图表密集页适当减少。不要按中文字数机械替换或缩小字体塞入英文长句；短标签、短标题优先，并检查英文大小写、行长、换行和所选西文字体。
- 一般内容页以80—180个汉字为起点，不含引用和表格。机制图页可更少，文献比较页可稍多，以投影可读性为准。
- 两份参考整体属于中高信息密度的学术技术报告。保留机制、条件、证据与解释，不能为了留白只剩大标题、三个关键词和装饰图；也不要照搬源稿的挤压、溢出和不可读小字。
- 避免一页放超过两个独立证据图；确有多子图时统一(a)(b)编号、图注和比较口径。
- 方法介绍保留输入、关键机制、输出、验证方式。拟创新点写清“相对哪类方法，改变哪一机制，如何验证”。
- 区分百分比提升与百分点差值，避免把目标数值写成测量结果。预期目标只有用户材料支持时才写具体数值。
- 标题采用“研究现状”“结构感知状态建模”“实验设计与评价指标”等明确主题，或有证据支撑的结论。不要强迫所有标题都写成宣传口号。

## content-plan.json

顶层为对象，`slides` 是按播放顺序排列的数组。以下是字段示意，不是研究内容示例：

```json
{
  "mode": "two-stage",
  "academic_use": "根据实际任务填写，如paper-reading或group-meeting",
  "slide_count": 18,
  "page_count_confirmed": true,
  "language": "zh-CN",
  "language_confirmed": true,
  "generation_preflight": {
    "status": "passed",
    "tool": "实际使用的工具",
    "model_requested": "gpt-image-2",
    "backend_verified": false,
    "reference_input_tested": true,
    "tested_at": "实际测试时间",
    "image": ".build/preflight/实际诊断图.png"
  },
  "image_stage_decision": "api",
  "global_image_profile": "实际共享配置路径；内置工具或跳过时为null",
  "copy_status": "draft",
  "copy_revision": 1,
  "copy_approval": null,
  "aspect_ratio": "16:9",
  "canvas": {"width": 1280, "height": 720},
  "duration_minutes": 15,
  "style_variant": "fusion",
  "slides": [
    {
      "id": "S09",
      "role": "method",
      "title": "从用户材料确定的方法名称",
      "message": "说明这一机制如何回应前述研究问题",
      "layout": "Method",
      "relation_type": "mechanism-with-explanation",
      "presentation_pattern": "main-diagram-plus-side-points",
      "reference_ids": ["B11"],
      "text_exact": ["最终逐字文本，按阅读顺序列出"],
      "sources": [{"id": "R01", "file_or_url": "实际来源", "locator": "页码或表号"}],
      "asset_paths": [],
      "data": null,
      "formula_latex": [],
      "evidence_status": "proposal",
      "expected_objects": {"text": 1, "table": 0, "chart": 0, "diagram_nodes": 0, "formula": 0},
      "speaker_notes": "说明假设、适用边界与真实引用",
      "notes": "生成和重建时需要保留的学术语义"
    }
  ]
}
```

实际文件的 `slides` 数量必须等于 `slide_count`，并从S01连续编号。`text_exact` 是必须出现在画面里的文本，不放旁白或给生成器的指令。`expected_objects` 是该页最低预期原生对象数；`text` 统计非空原生文本形状，不包括表格单元格和图表标签。流程节点采用 `diagram-` 命名前缀便于结构核查。数值必须放入 `data` 或引用外部数据文件，不能只存在提示词里。

`page_count_confirmed` 和 `language_confirmed` 表示来自用户回答或已有明确指令。`copy_status` 为 `draft` 时不得生成正式页面或制作PPT，启动的单张诊断图除外；用户明确确认后改为 `approved`，并在 `copy_approval` 记录对应原话或消息定位，不能伪造确认。`generation_preflight.status` 使用 `passed`、`failed`、`unavailable` 或 `not-required`，不得把仅检查配置记为通过；跳过生图时保留实际失败状态及用户选择，`mode=direct-editable`，不得捏造成功。项目报告还须核对首两页及末页的 `role` 分别为 `cover`、`agenda`、`closing`。实际项目的 `academic_use` 使用 `project-report` 或明确的项目报告类型。以上示例中的测试信息、时间与路径必须替换为实际值；项目文件不含API Key。

没有论文原文而只有少量摘要时，先完成有来源的部分，并在内容计划中标记待补信息。未补齐的关键方法、实验数据和机构信息不可在最终图片中表现为已确认内容。
